# GitHub App credential provider

`GitHubAppPublisherCredentialProvider` is an optional runtime component for a future protected publisher. Install its signer dependency with `python -m pip install '.[github-app]'`; development installs include the same extra so tests exercise RS256 signing.

Construct `GitHubAppCredentialPolicy` only from protected publisher configuration. It requires the App ID, installation ID, target repository ID and full name, App slug, and expected bot login. Supply the App private key through the trusted runtime’s secret mechanism; never place it in a profile, artifact, log, or pull-request-controlled input. The provider also requires a protected `VerifiedPublisherIdentity` from the trusted runtime canary. It fails before API access unless that identity is `VERIFIED`, has `APP_INSTALLATION` kind, and matches the policy’s App ID, installation ID, and bot login. The GitHub-reported bot login must match that same identity. Missing policy, key, or canary identity makes credential acquisition unavailable before API access.

For each new permission scope, the provider signs a short-lived App JWT and checks GitHub’s authenticated App, installation, and repository-installation responses. It then requests an installation token limited to the one configured repository and `actions:read` plus `pull_requests:read` or `pull_requests:write`. It verifies the returned permissions, expiry, repository visibility, and App bot login before constructing the existing typed credential. The identity evidence hash is stable across the read and write scopes because it represents App, installation, repository, and bot identity; each token’s permissions remain separately validated.

The returned identity evidence hash binds the protected canary evidence ID to the server-checked App, installation, repository, and bot user ID facts. The hash is stable across read and write scopes for the same canary and server identity. `VerifiedPublisherIdentity` does not carry a bot user ID or repository ID, so the provider verifies those against the protected policy and GitHub API and includes the observed bot user ID in its evidence hash; it does not claim a canary-side comparison for those fields.

The in-memory cache has separate entries for the exact read and write scopes. It reuses a token only when that scope matches and the token outlives the requested operation deadline. The provider does not automatically retry or rotate after GitHub denies a cached token; the denied operation fails. A later runtime must establish its own credential state.

Tests inject a synthetic typed canary identity as a fixture; those tests do not execute or prove a live canary. These API checks establish credential identity and scope for that request. They do not authorize a review, verify upstream artifact intake, or establish write-path safety. The current publisher workflow remains hard-disabled. Production use still requires a trusted target-repository publisher workflow, authenticated exact-head artifact admission, acknowledged pre-submit receipts, explicit owner authorization, and separately reviewed recovery controls.
