# Protected pull request analysis source

`templates/protected-pr-review-analysis.yml` is an inert example for a target repository that wants a protected, same-repository pull request source run. It listens to `pull_request_target`, passes the event's PR number/base/head as data, and invokes the existing reusable analysis workflow at a full commit SHA. The template's `if: false` is a hard stop. It does not activate analysis or publication; enabling the analysis source requires a separately reviewed change in the target repository.

The reusable call grants only `contents: read`, `checks: read`, `pull-requests: read`, and `actions: read`. It forwards the six analysis credentials explicitly: `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `JEV_BASE_URL`, `JEV_MODEL`, and `JEV_API_KEY`. Do not replace these mappings with `secrets: inherit`. The pinned reusable workflow must be reviewed at the exact SHA before those secrets are made available. Its analysis sends selected PR evidence to the configured model endpoints; the target owner must approve those endpoints and data flows. No GitHub App private key or publication credential belongs in this caller.

The caller must use the protected base-branch workflow context. GitHub documents that `pull_request_target` uses the base ref and the base-repository workflow file from the default branch; ordinary `pull_request` runs workflow code from the PR merge branch and uses a `refs/pull/<number>/merge` ref. The source contract keeps these identities separate:

- **Caller workflow identity:** `github.workflow_ref` and `github.workflow_sha` describe the target-local workflow file loaded from the protected base branch. Restrict accepted PRs to the target repository's protected default base branch. GitHub documents `github.sha` as the event commit and `github.workflow_sha` as the workflow-file commit, but does not promise those values are equal. A secretless context probe is provided at `scripts/protected_source_context_probe.py`; its inert workflow is `.github/workflows/protected-source-context-probe.yml`. It records the runner SHA, workflow SHA, API run head, and current PR base/head separately and reports equality observations without treating them as identity proof. Qualify an actual protected-base run before adopting any equality between these fields as a producer or receiver invariant. Never infer the caller workflow SHA from the PR head or the Actions run API's `head_sha`.
- **Source run identity:** repository, run ID/attempt, event, workflow ID/path, `head_branch`, and `head_sha` come from the GitHub Actions run API. Keep the API run's `head_*` values distinct from the caller workflow context and PR revisions. A read-only observation returned an empty `pull_requests` list for one `pull_request_target` run, so the receiver must not depend on that list to identify the reviewed PR. Qualify whether the API run's `head_branch/head_sha` match the PR head before relying on that additional binding.
- **Reviewed PR identity:** the wrapper passes the event's PR number, base ref/SHA, and head SHA to the reusable analysis as untrusted target claims. The analysis preflight checks them against the read-only PR API. The protected receiver may use the manifest's PR number only to select which PR to fetch; it must then independently fetch the current PR and compare repository, open state, default base branch, base SHA, and head SHA with the manifest before admission. The PR head SHA is never substituted for the caller workflow-file SHA or source-run `head_sha`.
- **Reusable harness identity:** `job.workflow_ref`, `job.workflow_sha`, repository, and path describe the called reusable workflow. The producer records these claims; the receiver independently checks the exact `referenced_workflows` entry and immutable SHA before requesting a write-scoped credential.

Replace both 40-zero harness placeholders with the same reviewed full commit SHA before a target owner considers enabling the source. Set the example `main` branch filter to the target's protected base branch. Keep the reusable workflow's publication bundle opt-in explicit. A produced artifact and its provenance file are claims that the protected publisher must re-fetch and validate; they do not authorize a review.

Before enabling the source, run the secretless context probe on a protected-base `pull_request_target` event and inspect its sanitized observations alongside the API response for the event, workflow ID/path, `head_branch`, `head_sha`, and called-workflow path/SHA. The probe is disabled by default and has no GitHub App or model-provider credentials. Use observed values to settle the source contract; do not assume the context SHAs are equal, or treat the run API `head_sha` as the workflow-file SHA. Independently compare the fetched current PR with the manifest. GitHub's documentation does not establish every field's shape in the REST workflow-run response. Verify that the target repository permits this event under its Actions event policy and that its default branch is protected.

The protected publisher also needs its own reviewed policy file, pinned caller/harness/profile identities, an installed GitHub App with the required repository scope, and separately approved write authorization. Those settings and live checks are pending. The checked-in publisher workflow remains hard-disabled, and this template makes no quality, semantic-accuracy, or publication claim.
