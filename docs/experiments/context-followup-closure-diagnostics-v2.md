# Context follow-up closure diagnostics v2

This document specifies additive, typed observations for the historical context-follow-up experiment. It does not change the frozen plan, primary requests, model/provider behavior, reducer decisions, call limits, or closure rules.

The durable engine result adds `closure_diagnostics` to required-context coverage rows. The experiment-only sanitized projection can report this as `required_context_closure_diagnostics` under `context-followup-observation.v2` only when the caller explicitly opts in with `include_closure_diagnostics=True`. Existing follow-up projection callers keep the v1 shape/schema by default. Projection v1 artifacts remain unchanged and must not be reinterpreted as v2.

The diagnostic records whether its inputs were observed, the aggregate coverage-note result, note count, first-failure counts from the existing `REQUIRED_CONTEXT` predicate, required-output quarantine count by a fixed kind allowlist, and counts of unresolved and nested follow-up gaps. A nested gap means an unresolved context-gap record was emitted by a `:followup:` task; it does not authorize recursive retrieval. `UNKNOWN` indicates absent, malformed, unbound, or out-of-contract durable data and must not be replaced by a zero count.

Coverage-note checks retain each current call site's source order. Follow-up resolution checks object shape, in-scope unit, `COVERED` state, `STATIC_REVIEW` basis, at least one required retrieved-evidence reference, then every note reference present in the dispatched input. The final coverage reducer checks object shape, `COVERED` state, `STATIC_REVIEW` basis, in-scope unit, then the same reference checks. The Boolean result is identical for canonical notes, while a note violating multiple conditions can receive a different first-failure code at the two call sites. One note contributes at most one code. The original `any(...)` short-circuits at the first matching note; diagnostics preserve that behavior and report how many later notes were not examined. A match does not cancel an unresolved nested gap or quarantine outcome.

The projection contains only closed enums and bounded counters. It excludes note text, prompts, response bodies, proposal target and rationale, evidence references, exception strings, raw provider output, and provider billing claims. An HTTP status 200 or worker `SUCCEEDED` status is not evidence of semantic coverage or a provider-side call receipt.

When validating the change, compare all frozen primary request descriptors and hashes, the 47 request count, 124 obligation identities, and 4,002,927 serialized primary-input bytes. Also compare dispositions, coverage states/reasons, reservations, settlements, and call counters on deterministic fixtures. Any change to those values is a stop condition; diagnostics are not an acceptance policy.
