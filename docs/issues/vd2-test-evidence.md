Receipt writes are fake writer/upload calls, not proof of a durable live artifact.

The GitHub 429 row fails closed during read-only history scanning, before receipt upload or review POST. The GitHub 503 row is deliberately narrower: it occurs during history reconciliation after an ambiguous submit and preserves `UNKNOWN` with one prior POST and one receipt upload. Neither row is a generic claim that every GitHub endpoint/status is covered. The redirect row tests only artifact-download admission: an untrusted location raises an exception matching the listed reason and an allowlisted signed download succeeds without the API token. It does not assert an engine/publisher terminal state or exact POST/receipt counts; those cells are explicitly unasserted.

Conflicting budget replay remains covered separately by [test_conflicting_duplicate_attempt_replay_cannot_replace_terminal_failure](../../tests/test_vd2_provider_faults.py): a conflicting successful replay cannot replace the existing failed settlement or add outputs. It is not a provider duplicate-response scenario.

This is a bounded fault-acceptance evidence slice, not full VD-2 closure or live-provider/GitHub qualification. Reconcile's historical score excludes 338 no-tests mutants from its denominator; denominator treatment and qualification of the complete named mutation scope remain unresolved. The historical percentages below do not close those gaps. Remaining mutation/property/coverage requirements and faults outside the indexed existing cases retain their own gates. The timeout fixture separates a bounded five-second isolated-process startup allowance from the provider's injected 0.05-second HTTP timeout; it does not change production deadlines or retry policy.
