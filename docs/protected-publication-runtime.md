# Protected review publication runtime

The protected runtime composes the existing GitHub Actions artifact intake, credential checks, publication admission, receipt uploader, and single-review publisher. It accepts a review result artifact from a completed `pull_request_target` run on the protected default branch. The artifact may identify the PR, but it cannot choose policy, credential identity, repository, workflow pins, disposition scope, or whether publishing is enabled.

The current `.github/workflows/pr-publish.yml` remains disabled and does not invoke this module. The runtime expects `.github/pr-review-publisher-policy.json`, but that policy file is not present in this checkout, so a direct invocation currently fails closed. Adding and pinning that file, changing it to `enabled: true`, or adding a workflow caller are separate owner-reviewed activation decisions. This runtime has no live-provider test or deployment qualification.

When enabled by a protected configuration, the runtime verifies its clean checked-out source revision and policy file, then uses its Actions job token for read-only bootstrap requests to bind the source run and fetch one bounded, digest-checked result artifact. It extracts only the PR number and base/head SHAs as candidate target data. The App identity verifier checks GitHub-reported App, installation, repository, bot, source-run, and PR facts before requesting the private key; its read-only identity check is neither publication authorization nor deployment qualification. Full artifact intake and adapter admission run before any write-scoped App token. The existing publisher requires an uploaded receipt to be re-fetched and verified, checks the PR head again, and makes at most one review POST. Missing, stale, ambiguous, or unacknowledged evidence stops the operation.

The target is restricted to PRs whose base repository is the protected workflow’s repository and whose current base ref is the configured default branch. A fork head remains untrusted source data; it cannot select the publisher repository, credentials, or executable runtime. Before reading the artifact or App key, the runtime fetches the configured default branch from GitHub's repository API and binds the manifest's caller workflow SHA to that reported tip. It keeps the reviewed PR base/head SHAs separate: an older open PR may have a base commit behind the current default-branch tip. The App identity canary independently re-fetches the branch tip before reading the key. Before receipt persistence and again after receipt acknowledgement, the runtime rechecks that the tip is unchanged and that the PR still has the candidate base/head. These are fail-closed API observations; the source-context probe records `GITHUB_SHA`, `GITHUB_WORKFLOW_SHA`, the default-branch API tip, run API head, and PR base/head separately. Do not assume unobserved context equality or treat the probe as identity proof. The producer must independently bind its caller workflow SHA to the protected source revision. Manual dispatch and cross-repository publication remain outside this runtime.

The policy file is a versioned contract, not an input to the PR analysis. Schema v1 is App-only and remains unchanged. Schema v2 explicitly selects the App route or the target job's Actions token route and requires `authorization_mode: STANDING_BOUNDED`; this records narrow owner authorization for every result matching the exact policy envelope, without per-result human approval. Both templates remain disabled. The policy pins the repository and numeric ID, source and publisher workflow IDs/paths/refs, called harness commit, profile and provider-configuration identities, allowed disposition/event scope, credential route and expected actor, artifact redirect hosts, and upper bounds for run/page/review counts and wall-clock time. V2 also pins the exact publisher workflow file SHA-256; the runtime compares that digest with both the checked-out file and the file at `GITHUB_SHA` before accessing GitHub or the token. A target-local owner must review every identity and limit against authoritative repository configuration while keeping `enabled` false. The runtime also requires the workflow checkout to be clean and its HEAD to equal `GITHUB_SHA`; it rejects an uncommitted or mismatched policy file.

For v2 `ACTIONS_TOKEN`, the runtime consumes only the protected workflow's fixed `${{ github.token }}` binding and validates the publisher workflow bytes against the policy's SHA-256 pin before any GitHub API request or token read. It also validates source/run/repository facts through bounded API admission. `PLATFORM_BOUND` means token provenance is bound to that exact protected workflow and those API facts; it does not mean the opaque token was independently inspected or that GitHub's effective write scope was observed. The v2 pre-POST receipt records the complete declared writer-job permission map and workflow digest with `permission_basis: WORKFLOW_DECLARATION` and `write_capability: NOT_TESTED`. The adapter's narrower `actions`/`pull-requests` tuple describes the operations it needs, not the full effective token permissions. Only the actual review response and later history readback showing the expected `github-actions[bot]` actor can establish that exact effect as confirmed. Actor mismatch or missing readback after submission leaves the result `UNKNOWN`; there is no App-key fallback or automatic retry. The existing App route remains `VERIFIED` through its separate App/installation APIs and token scope response.

The writer adapter uses repository-wide concurrency (`pr-review-publish-<repository-id>`) so two PRs in the same repository cannot overlap receipt and review effects. The workflow template queues runs and does not cancel an in-progress publisher. The App route requires its named `code-review-publication` environment and App key secret; the Actions-token route uses no App key or installation and instead relies on the target workflow's per-job token. In either route, the YAML declaration does not prove configured protections or effective write capability.

The installed module entry point is:

```sh
python -m pip install '.[github-app]'
python -m pr_review_harness.protected_publication_runtime
```

Run it only inside a protected GitHub Actions runner that supplies these trusted platform inputs: `GITHUB_WORKSPACE`, `GITHUB_SHA`, `GITHUB_REPOSITORY`, `GITHUB_REF`, `GITHUB_WORKFLOW_REF`, `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, and an absolute `GITHUB_EVENT_PATH` containing the `workflow_run` event. It also needs a target-scoped `GITHUB_TOKEN`, plus `ACTIONS_RUNTIME_TOKEN`, `ACTIONS_RESULTS_URL`, and `ACTIONS_RUNTIME_URL` for the official artifact uploader. The App route additionally needs `PR_REVIEW_GITHUB_APP_PRIVATE_KEY` as a protected secret; runtime code requests it lazily only after source and current-PR checks. The Actions-token route needs no App key, but its writer job must declare the minimum permissions needed for source checkout, artifact/history reads, and review creation; with the current checkout this includes `contents: read`, `actions: read`, and `pull-requests: write`. GitHub may further restrict effective permissions. YAML is a declaration, not proof of write capability. Never populate policy fields from PR artifacts or command-line arguments.

For local, provider-free verification, run the focused fake-API composition tests with:

PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 PYTHONPATH=src python3 -m pytest -q \

These tests verify control flow and API binding against fakes. They do not establish live GitHub API behavior, provider quality, or permission to enable the workflow.
