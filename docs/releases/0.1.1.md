## Scope: signed provenance for the same source-only distribution

`0.1.1` keeps the `0.1.0` source-distribution shape and adds a signed,
GitHub-native build provenance attestation:

* the release publishes only the wheel and source distribution built from the
  tagged commit, plus their checksums, CycloneDX SBOM, unsigned
  `provenance.json`, reproducibility report, and notes;
* no package is published to PyPI and no index or registry is written;
* no container image, hosted service, or deployment is part of the release;
* the release build job attests the wheel and sdist with a keyless GitHub OIDC
  identity after their checksums, SBOM, and provenance have been verified.

Installing `0.1.1` means installing the attached wheel or building from the
source archive or a source checkout. There is no hosted component to adopt.

## What changed in 0.1.1

* The release `build` job now runs the SHA-pinned
  `actions/attest-build-provenance` v2.4.0 action with `subject-path` covering
  `dist/*.whl` and `dist/*.tar.gz`. One attestation binds both distribution
  digests to this repository, workflow, and source revision.
* The build job requests only the permissions required for keyless
  attestation: `contents: read`, `id-token: write`, and `attestations: write`.
  It does not receive `contents: write`; only the `publish` job can create the
  GitHub Release.
* The unsigned `provenance.json` and CycloneDX SBOM remain release assets. The
  attestation is an additional signed layer, not a replacement for the
  inspectable unsigned evidence.
* Consumer verification documentation now covers both the checksum/SBOM layer
  and `gh attestation verify`.

The complete classified change list is the `0.1.1` section of
[`CHANGELOG.md`](../../CHANGELOG.md).

## Verify the release

Verify the checksums first; `SHA256SUMS` covers the evidence files as well as
the distributions, so a tampered SBOM or provenance file fails the check.

```sh
gh release download v0.1.1 --dir /tmp/pr-review-release
cd /tmp/pr-review-release
sha256sum -c SHA256SUMS
```

Then verify the signed build provenance attestation for each distribution
against this repository. The general form is
`gh attestation verify <artifact> --repo groktopus/codereview`; for the `0.1.1`
assets:

```sh
gh attestation verify ./pr_review_harness-0.1.1-py3-none-any.whl \
  --repo groktopus/codereview
gh attestation verify ./pr_review_harness-0.1.1.tar.gz \
  --repo groktopus/codereview
```

A passing `gh attestation verify` result establishes that the attestation was
issued by this repository's release workflow for that exact artifact digest.
It does not establish review quality, source correctness, or production
readiness, and it does not replace the checksum and SBOM checks.

Check that the SBOM, provenance, and checksums agree with the downloaded files,
using the verification script from the same tag:

```sh
git clone https://github.com/groktopus/codereview /tmp/pr-review-repo
git -C /tmp/pr-review-repo checkout v0.1.1
python3 /tmp/pr-review-repo/scripts/verify_release_artifacts.py \
  --dist /tmp/pr-review-release \
  --sbom /tmp/pr-review-release/pr-review-harness-0.1.1.cdx.json \
  --provenance /tmp/pr-review-release/provenance.json \
  --checksums /tmp/pr-review-release/SHA256SUMS \
  --source-revision "$(git -C /tmp/pr-review-repo rev-parse HEAD)" \
  --workflow-ref "groktopus/codereview/.github/workflows/release.yml@refs/tags/v0.1.1"
```

The expected script result is `Release verification: PASS (signed: no)`: that
script verifies the unsigned `provenance.json`/SBOM layer, while the signed
attestation is verified separately with `gh attestation verify`.

Verify the tag and package metadata against the same checkout:

```sh
git -C /tmp/pr-review-repo fetch --tags
git -C /tmp/pr-review-repo rev-parse --verify 'v0.1.1^{commit}'
python3 /tmp/pr-review-repo/scripts/check_version_policy.py \
  --root /tmp/pr-review-repo --tag v0.1.1
```

Finally, install the wheel in a fresh environment outside the checkout and start
the CLI:

```sh
python3 -m venv /tmp/pr-review-release-venv
/tmp/pr-review-release-venv/bin/python -m pip install ./*.whl
/tmp/pr-review-release-venv/bin/pr-review --help
```

## Provenance and signatures: two layers

Starting with `0.1.1`, provenance has two distinct layers:

* **Signed attestation.** The wheel and sdist are covered by a keyless GitHub
  OIDC build provenance attestation. GitHub exchanges the workflow's OIDC token
  for a short-lived Sigstore signing certificate, so no long-lived private key
  or repository secret is used. The attestation is stored by GitHub's
  attestations API and is not listed in `SHA256SUMS`.
* **Unsigned inspectable evidence.** `provenance.json` is an in-toto Statement
  v1 with an SLSA provenance v1 predicate, but its `signing.status` is
  `unsigned`. Its builder identity and workflow fields are self-asserted by the
  release script. The CycloneDX SBOM is also unsigned.

The earlier `v0.1.0` release was published before the attestation step existed:
`v0.1.0` remains unsigned and has no GitHub attestation. Do not describe
`v0.1.0` as attested, and do not treat an attestation for a later version as
covering `v0.1.0` artifacts. `SHA256SUMS` is a checksum list, not a signature,
and the release workflow does not verify tag signatures.

## What this release does not claim

* **No production-readiness claim.** `0.1.1` is a pre-1.0 source release. It is
  not asserted to be production-ready, and no operational adoption is part of
  this release.
* **No replacement claim.** Nothing here replaces Droid or any other reviewer,
  and no cutover is authorized by this release.
* **No review-quality or accuracy claim.** Model agreement, a passing test
  suite, and a valid attestation are not calibrated evidence about review
  quality.
* **No publication effect.** `pr-review publish` is a read-only preview, the
  central publisher job is hard-disabled, and live publication requires a
  separate, explicit authorization.
* **No bit-for-bit reproducibility claim.** The retained reproducibility report
  is authoritative for the observed result; with the current setuptools
  toolchain the source distribution is content-reproducible rather than
  byte-identical, while the wheel was byte-identical in the recorded `0.1.0`
  run. `0.1.1` records its own result.
* **No PyPI or package-index availability.** Installation is from the attached
  wheel or from source.

## Known limitations

* The signed attestation authenticates the release workflow and artifact
  digests; it does not authenticate the correctness, security, or quality of
  the source itself.
* `provenance.json` and the SBOM remain unsigned, self-asserted evidence.
* The SBOM inventories the wheel and source distribution and their metadata; it
  does not enumerate every file inside the archives, and it does not cover
  development dependencies.
* The release workflow's behavior is established only by a real release run; a
  merged workflow file is not evidence that a release exists.
* Version and contract identities move independently; pin both the package
  version and the contract identities you consume
  ([VERSIONING.md](../VERSIONING.md),
  [CONTRACT-REGISTRY.md](../CONTRACT-REGISTRY.md)).
* Provider, GitHub, and model availability are outside the version promise.
