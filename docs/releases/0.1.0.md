## Scope: a source-only distribution

`0.1.0` is a source-only release in the sense that the release distributes
source-built artifacts and nothing operational:

* the only artifacts are the wheel and the source distribution built from the
  tagged commit, plus their checksums, SBOM, provenance, reproducibility report,
  and notes;
* no package is published to PyPI and no index or registry is written;
* no container image, hosted service, or deployment is part of the release;
* no target repository's review automation is changed, and the central
  publication job remains hard-disabled.

Installing `0.1.0` means installing the attached wheel or building from the
source archive or a source checkout. There is no hosted component to adopt.

## What is included

The complete classified change list is the `0.1.0` section of
[`CHANGELOG.md`](../../CHANGELOG.md). In summary:

* the `pr-review` CLI (`review`, preview-only `publish`, `stats`) over a
  deterministic snapshot, planner, scheduler, budget, and disposition pipeline;
* an OpenAI-compatible primary review provider with optional advisory Jev and
  native claim-assessment adapters;
* bounded context selection, external check ingestion, claim reconciliation, and
  incomplete-reason reporting;
* the contract/version registry, versioned artifact schemas, the hash-locked
  development environment, and the install/support matrix;
* the frozen 41-case evaluation corpus, the QM-2 labeling protocol, and the QM-3
  scorecard gate — evidence infrastructure, not evidence of review quality;
* release supply-chain evidence (SBOM, unsigned provenance, reproducibility
  check, asset checksums) and the tag-gated release workflow;
* decision records, ownership and backlog records, and the read-only security
  workflows.

## Verify the release

Verify the checksums first; `SHA256SUMS` covers the evidence files as well as the
distributions, so a tampered SBOM or provenance file fails the check.

```sh
gh release download v0.1.0 --dir /tmp/pr-review-release
cd /tmp/pr-review-release
sha256sum -c SHA256SUMS
```

Then check that the SBOM, provenance, and checksums agree with the downloaded
files, using the verification script from the same tag:

```sh
git clone https://github.com/groktopus/codereview /tmp/pr-review-repo
git -C /tmp/pr-review-repo checkout v0.1.0
python3 /tmp/pr-review-repo/scripts/verify_release_artifacts.py \
  --dist /tmp/pr-review-release \
  --sbom /tmp/pr-review-release/pr-review-harness-0.1.0.cdx.json \
  --provenance /tmp/pr-review-release/provenance.json \
  --checksums /tmp/pr-review-release/SHA256SUMS \
  --source-revision "$(git -C /tmp/pr-review-repo rev-parse HEAD)" \
  --workflow-ref "groktopus/codereview/.github/workflows/release.yml@refs/tags/v0.1.0"
```

The expected result is `Release verification: PASS (signed: no)`. The
`signed: no` is expected and is not a failure; see the next section.

Verify the tag and package metadata against the same checkout:

```sh
git -C /tmp/pr-review-repo fetch --tags
git -C /tmp/pr-review-repo rev-parse --verify 'v0.1.0^{commit}'
python3 /tmp/pr-review-repo/scripts/check_version_policy.py \
  --root /tmp/pr-review-repo --tag v0.1.0
```

Finally, install the wheel in a fresh environment outside the checkout and start
the CLI:

```sh
python3 -m venv /tmp/pr-review-release-venv
/tmp/pr-review-release-venv/bin/python -m pip install ./*.whl
/tmp/pr-review-release-venv/bin/pr-review --help
```

## Provenance and signatures: unsigned

The release evidence is unsigned by design and must not be described as signed,
attested, or verified in the cryptographic sense:

* `provenance.json` is an in-toto Statement v1 with an SLSA provenance v1
  predicate, but its `signing.status` is `unsigned` with no signature and no
  certificate. It records the source revision, workflow reference, builder
  identity, build command, and artifact hashes; the builder and workflow fields
  are self-asserted by the release script.
* There is no Sigstore signature and no GitHub artifact attestation. The
  workflow requests neither `id-token: write` nor `attestations: write`.
* `SHA256SUMS` is a checksum list, not a signature.
* A signed tag (`git tag -s`) is a local operator practice only: the release
  workflow does not verify tag signatures.
* `verify_release_artifacts.py --require-signed` fails by design until
  cryptographic signature verification is implemented, even for provenance that
  claims a signature.

What a consumer can establish is integrity and recorded build inputs: the
downloaded bytes match the checksums, the SBOM and provenance subject hashes
match those bytes, and the provenance names a source revision and workflow ref.
Origin authenticity is not authenticated.

## What this release does not claim

* **No production-readiness claim.** `0.1.0` is a pre-1.0 source release. It is
  not asserted to be production-ready, and no operational adoption is part of
  this release.
* **No replacement claim.** Nothing here replaces Droid or any other reviewer, and
  no cutover is authorized by this release. The evaluation corpus has no quality
  labels yet and the scorecard reports missing data instead of accuracy.
* **No review-quality or accuracy claim.** Model agreement, a passing test
  suite, and a clean artifact verification are not calibrated evidence about
  review quality.
* **No publication effect.** `pr-review publish` is a read-only preview, the
  central publisher job is hard-disabled, and live publication requires a
  separate, explicit authorization. A separately installed target-local route is
  outside this release and is described in [STATUS.md](../STATUS.md).
* **No bit-for-bit reproducibility claim.** The retained reproducibility report
  is authoritative for the observed result; with the current setuptools
  toolchain the source distribution is content-reproducible rather than
  byte-identical, while the wheel was byte-identical in the recorded run.
* **No PyPI or package-index availability.** Installation is from the attached
  wheel or from source.

## Known limitations

* Artifacts and provenance are unsigned (above).
* The SBOM inventories the wheel and source distribution and their metadata; it
  does not enumerate every file inside the archives, and it does not cover
  development dependencies.
* The release workflow's behavior is established only by a real release run; a
  merged workflow file is not evidence that a release exists.
* Version and contract identities move independently; pin both the package
  version and the contract identities you consume
  ([VERSIONING.md](../VERSIONING.md),
  [CONTRACT-REGISTRY.md](../CONTRACT-REGISTRY.md)).
* Provider, GitHub, and model availability are outside the version promise.
