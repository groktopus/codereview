# Historical SlopSearX trial

This manual workflow runs the installed review CLI on three frozen historical PR base/head pairs. It is an evidence-collection experiment; it does not test current PR state, establish review quality, authorize cutover, or approve a release.

The inputs under `docs/real-case-trial-v1/` pin the case identities, profile and historical-check files, required-scope hashes, exact primary request descriptors, and byte-level request hashes. Runtime provenance v2 pins review-harness commit `607825028044890ba939000449e3d6df655ec3f3`, verifies the installed package against the source, and records the verified 28-module inventory and aggregate hash `465fd21781221b01188f08fbbeece9457cc58e08025d9827845de427ac9a67d1` separately from the runner revision. Relative to runtime `54b8fb5e8bb3b1ac8681dff1d0ff7143b7318215`, only `claim_assessment.py` changed; the update accepts a configured per-task input allowance above the native 64,000-byte request ceiling, then checks the exact serialized request against both limits before quote, reservation, or HTTP. It preserves the fixed cases, request receipts, budgets, endpoints, and models; it does not establish better review quality. The prior full-three-case run `36322270184` used runtime `54b8`, so it does not exercise this correction. A new provider-free prepare-only receipt against `6078` is required to reverify the runtime identity and frozen request rows before a later provider trial. This provenance is distinct from retained v1 receipts produced from `77abf7b9b46c0dc1d077ab267ee4d77cf7781998` and prior 6bd trial artifacts; those historical receipts remain unchanged. It reads the pinned SlopSearX Git objects from a supplied bare repository (or fetches the pinned objects into a temporary bare repository in the hosted workflow), reconstructs the ordinary Git diff with a command-scoped Python diff driver, verifies its frozen digest, and invokes the normal CLI against that bare store. It does not check out or execute SlopSearX code.

The workflow accepts two fixed actions and two fixed scopes. `prepare-only` runs the normal CLI's exact request serializer without provider calls or provider credentials. It must match every pinned snapshot, scope, evidence-index, and primary request hash before writing a preparation receipt. `provider-trial` is a separate manually selected action and requires the six repository secrets `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, `JEV_BASE_URL`, `JEV_MODEL`, and `JEV_API_KEY`. The base URL inputs follow the normal production translator contract: API roots without the final route. The runner passes the six values through `scripts/provider_config_from_env.py`'s shared translator, then enforces the fixed resulting endpoint and model identities; callers cannot select another identity.

The first staged provider trial, Run `36313718569`, stopped atomically during `provider_configuration` after 0.08 seconds with `provider_identity_configuration_mismatch`. No unchanged-source retry was made. The run did not report which input first mismatched, so this record does not attribute the failure to a particular secret value. Source review identified a contract defect in the trial runner: it compared `JEV_BASE_URL` to the final `/systemone` endpoint before invoking the production translator, which accepts an API root and appends that route. The correction delegates validation and config construction to the production translator, then checks the resulting endpoint and model identities. This is a source-specific explanation supported by the normal translator contract; it is not a claim about the unreported first mismatch in that run.

The prior full-three-case trial, Run `36322270184` (runner caller `4935c54888bff8ace50ff47bf45b2e1be8f93fc9`, runtime `54b8fb5e8bb3b1ac8681dff1d0ff7143b7318215`), completed its bounded workflow and uploaded the sanitized result. Each case remained `PARTIAL` / `INCOMPLETE`; the run produced three structurally valid primary candidates total, and all three optional claim assessments failed locally with `invalid_input_byte_limit`. The source cause is the assessment adapter validating the configured per-task allowance (128,000 bytes) against the native request maximum (64,000 bytes) before serializing or measuring the actual candidate request. This rejects the broader harness allowance itself, even when an individual claim body could fit within the native cap; the run therefore contains no TypeSafe claim judgment to interpret. That run used runtime `54b8`, before the caller-limit correction now pinned at `6078`. The correction separates the caller ceiling from the native hard maximum, then checks the exact serialized request against both before quoting, reservation, or HTTP. It retains the exact request bytes and hashes, does not truncate or remove evidence, and still rejects an actual request over 64,000 bytes atomically. The transport's 64,000-byte request/response ceilings and existing response-versus-IPC accounting are unchanged. Per-case call reservations were 16/36/19; they are not actual-call counts. Actual total provider calls and cost remain `UNKNOWN`, and these failed assessments are not semantic labels or evidence of model quality.

The `staged-pr464` scope runs the PR-464 AUTO profile with a 24-call cap. This is an operational probe; it does not replace the full comparison. The `full-three-case` scope runs PR-457 and PR-463 in their frozen DEEP modes and PR-464 in AUTO, sequentially, with a 64-call cap per case. Both modes preserve the measured required scopes. Any missing scope, changed request, timeout, invalid provider output, candidate-projection problem, or exhausted limit leaves the case incomplete or unknown; the runner does not raise caps or retry.

Primary requests are limited to 128,000 serialized bytes each and 8,000,000 cumulative context bytes per case. Snapshot source context has a separate 300,000-byte aggregate ceiling; the shared response reservation is at most 32,768 bytes per call and 2,097,152 bytes per case. Primary output is capped at 1,800 tokens and 16,000 bytes. The four-call claim-assessment ceiling, semantic adjudication, follow-up, summary advisory, and Jev calls share the same call ledger. Their dynamic demand is unknown before a provider run. The engine deadline is 600 seconds per case; the wrapper stops each case at 660 seconds. The full workflow has a 55-minute outer timeout. No price is configured or inferred, so cost remains unknown.

The model-visible content is the normal CLI snapshot: the pinned profile and base-revision allowlisted context, changed-file evidence, and prepared request bodies recorded by their per-request SHA-256 receipts. The separate packet `review-task.md` and PR-464 `spec-requirements-excerpts.md` are not passed to the CLI and are not additional instructions. The profiles select project context from immutable base commits; the uploaded sanitized manifest retains each exact exposed request binding and content hash. The check runs completed on September 21, while the fixed normalization envelopes were captured on September 27; neither timestamps the current PR state or constitutes current CI evidence. `prepare-only` makes no provider calls and uses no provider credentials, but it does acquire the immutable Git objects over read-only HTTPS.

The 600-second engine deadline applies within each case; the 660-second case budget includes a 15-second cleanup reserve. A single 1,980-second matrix deadline starts before checkout and setup and includes a 30-second finalization reserve. The workflow's 55-minute job timeout is an outer platform safety limit, not additional trial runtime. The post-fetch bare-object acceptance ceiling is 200,000 total loose-plus-packed objects and 300,000 KiB of pack data. These checks run after fetch and do not bound peak transfer or disk use.

Provider result files, raw HTTP output, temporary Git object stores, and private config files stay under the runner's temporary directory and are removed before artifact upload. The only uploaded files are `summary.json` and `manifest.json`. The manifest contains a bounded allowlist projection of candidate narratives, their evidence locations and hashes, reconciliation status, semantic and Jev assessment fields, and identity hashes. Before writing, the runner scans JSON string keys and values for exact configured credential values and endpoint/model identity canaries, including values that JSON serialization escapes. This is a narrow canary check: it does not detect paraphrased, transformed, partial, or unrelated private content, and bounded assessment text may quote prompt evidence. Treat provider-generated assessment text as untrusted; the scan is not proof that prompts, configuration, or other private information were never echoed. If projection fails or exceeds its cap, unsafe content is omitted and the case is marked incomplete. A successful process status means only that the bounded run completed; any disposition, finding, coverage gap, or abstention must be reviewed separately. Valid findings outside any historical reference set remain visible and are not called accuracy errors.

On a handled acquisition, preparation, CLI, projection, or finalization error, the runner emits a nonzero status and writes the previously scanned case rows with the active case marked `INCOMPLETE` and later cases `NOT_RUN`. A provider-stage failure records provider call count and cost as unknown. If private-data cleanup or sanitized failure-artifact serialization fails, the summary and manifest may be unavailable; the workflow does not claim that all cases completed. Hard runner termination is outside this recovery guarantee.

The limits and runtime provenance are explicitly versioned in the new manifest; historical `77ab` receipts are not rewritten. The workflow has `contents: read` only. It does not query current PR metadata, run tests or application code from SlopSearX, publish a review/comment, merge, or deploy. The separately selected `provider-trial` action uses the already authorized fixed payload and endpoint bindings.
