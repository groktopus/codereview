# Model-only shadow audit v1

The shadow runner performs three bounded calls over one frozen case packet:

1. A source-only OpenAI-compatible auditor receives the frozen task and cited source evidence. Its output is sealed locally before Jev is called, and its request never includes the writer candidate.
2. The existing `ClaimAssessmentAdapter` asks Jev to classify that candidate against the same evidence.
3. A separate claim-facing auditor receives the candidate, Jev's typed classifications, and only the cited source evidence. It does not receive the source-only auditor output.

The CLI is `scripts/run_shadow_audit.py`. It requires `--live` before it can dispatch. It permits at most one call per stage, has per-request byte limits and a finite deadline, does not retry, execute target code, or publish a review. Run with a reviewed `model-only-shadow-case.v1` JSON packet, separate provider configs, a trusted TypeSafe decision config, and a new output directory. The emitted manifest contains statuses, identities, and hashes. Exact request and structured-response bytes remain in mode-0600 files beneath a mode-0700 output directory; do not upload those files as CI artifacts.

The packet must carry the full original snapshot. Its `snapshot_hash` is recomputed using the harness snapshot contract over every snapshot field other than `snapshot_id` and `snapshot_hash`. The frozen PR-457 trial material in `docs/real-case-trial-v1` contains its snapshot digest and evidence bindings, but not the full snapshot payload, so that material alone cannot be used to reconstruct or claim verification of the original snapshot.

The same-job continuation in `.github/workflows/private-shadow-capture.yml` is manual and opt-in. The selected-case writer stage (six calls for PR-457 or ten for PR-464) requires a fresh provider-free exact-request preflight and matching configured provider identity. Private writer capture disables the provider's optional semantic-adjudication stage, so only exact pinned primary writer requests can dispatch. The audit config step requires a successful sanitized writer receipt, and audit dispatch requires successful config validation. `AuditDispatchGuard` checks each exact serialized source-LLM, Jev, then claim-LLM request immediately before dispatch; the claim request is checked after Jev returns because it depends on that response. The runner selects at most one candidate packet by the pinned writer-plan task order, then packet SHA-256 within a task; model-produced candidate text does not control selection. It permits three audit calls maximum, zero retries, 64 KB request and response caps, 1,800 output tokens per LLM call, and 90 seconds per call. If no packet contains a candidate, it makes zero audit calls and records an explicit `incomplete` result with all three roles `not_run`. The upload allowlist contains the hash-only writer receipt, a separate bounded writer outcome summary, a hash-only workflow-status receipt, and the hash-only audit receipt. The writer outcome summary reports per-task-hash response parse status, returned finding-candidate count, packet candidate count, and one of four outcome enums; it distinguishes an empty model array from malformed specialist output and candidates absent after reconciliation/filtering. It contains no candidate text. Raw packet, request, response, and manifest files remain in the private job workspace and are deleted on job completion.

Audit receipts distinguish request attempts from provider calls. `role_call_counts` counts requests captured at a role boundary, including guard-rejected attempts; each such request retains only its SHA-256 in the sanitized receipt. `role_dispatched_call_counts` and `audit_provider_calls` count only roles with local evidence that the HTTP transport was entered. Guard-rejected attempts, requests that passed the guard but failed before transport (for example, missing credentials), and requests whose dispatch state is unknown are reported separately in `role_guard_rejected_counts`, `role_post_guard_pretransport_counts`, and `role_unknown_dispatch_counts`. HTTP-attempt evidence records local transport entry only; it does not prove remote receipt or provider consumption.

`private_capture.export_case_packets` writes packets to a unique private staging directory, publishes the completed directory, then atomically replaces the manifest with `case_packet_inventory` containing every relative packet filename and SHA-256. The shadow runner, writer receipt sanitizer, and deterministic packager compare the exact inventory with the directory and verify packet bytes before selection or packaging. A crash between directory publication and manifest replacement leaves no inventory and fails closed. The frozen PR-464 shadow plan pins the updated source module tree and plan digest; the historical preparation runtime pin remains separate. Tests cover multiple candidates, packet removal, and changed packet bytes. Do not infer zero candidates from an unbound or incomplete packet directory.

The workflow binds writer dispatch to the fresh exact provider-free preflight and configured identity, then binds audit configuration and dispatch to writer-receipt sanitization and config validation. PR #99 adds exact request checks at the dispatch boundary before credential lookup or transport. The claim-auditor request is constructed from Jev's runtime response, so it is checked after Jev returns and immediately before claim-auditor dispatch. Controlled model-stage failures produce terminal role states and a hash-only receipt. If packet/config validation or artifact I/O fails before a receipt can be written, sanitization fails closed, no audit artifact is uploaded, and always-run cleanup removes the private workspace. A completed package would establish traceable model-only observations only, not accuracy, correctness, ground truth, or truth labels.

`pr-review review --private-shadow-capture DIR` now opts a fresh read-only review into a separate private capture directory. The directory must be new and separate from ordinary output. It stores the full frozen snapshot, task-local source evidence, bounded exact provider request bodies, exact structured message-content bytes returned by the provider, call receipts, and one `case-packets/*.json` file per admitted candidate or task without a candidate. The request and response files are mode 0600 under mode 0700 directories; they must never be uploaded as Actions artifacts. The ordinary result and stdout do not include those bytes. Failed or interrupted calls retain explicit incomplete/failed receipts rather than a fabricated response. This captures local request bodies and structured message content, not authenticated remote wire delivery or the full HTTP envelope.

Capture is disabled for resume, prepare-only, and dry-run. The separate `--private-shadow-preflight-case-id PR-464` option is permitted only with provider-free `--prepare-only`; it creates no capture artifacts and only selects the same identity-independent full-snapshot digest used later by live capture. This narrow mode keeps ordinary historical review hashes unchanged while allowing the provider-free request descriptors and live capture to bind to one frozen digest. Generated historical check-run evidence is bound to the final snapshot ID in both this scoped preflight and live capture before hashing; ordinary historical reviews retain their previous evidence and hash behavior. The workflow verifies that exact prepared digest and all ten writer request descriptors before checking provider identity or dispatching. A stale or mismatched plan is rejected before the provider boundary; hosted run `36390722563` hit this rejection because its frozen snapshot pin did not match the runtime capture digest, so it is not evidence of writer quality or provider behavior. In GitHub Actions live capture requires the reviewed `groktopus/codereview/.github/workflows/private-shadow-capture.yml` manual workflow on `main`, an explicit trusted marker, and a new direct child of `RUNNER_TEMP`. A repository secret or PR input cannot select the capture destination. The workflow must verify its checked-out commit equals `GITHUB_SHA` before review dispatch; the capture option alone does not establish that property. The capture exporter checks that each candidate is from its own task-local provider response and admitted final finding, but the v1 shadow runner still declares the writer role from the packet. Until the separate deterministic packager verifies the packet and exact writer artifacts together with the three audit roles, do not claim a complete four-role v2 comparison.

All model judgments are advisory. Unknowns, abstentions, incomplete output, and failures remain explicit. These outputs do not establish accuracy, ground truth, or release readiness. The injection fixture verifies that source text is delivered as untrusted data and does not cross stage boundaries; it does not measure model resistance to prompt injection.

## Complementary evaluation when human labels are unavailable

Human adjudication is unavailable for this project. Do not leave it as a presumed future source of labels or use model-generated labels to fill that role. Retain any model-produced screen with `reviewer_kind: model_teacher`; `unknown` or missing provenance is never human. The model-only evidence track can qualify whether a bounded, read-only shadow was executed and audited. It cannot estimate semantic accuracy, precision, recall, error rates, calibration, or truth.

The hosted preparation/live-writer observations and the remaining full-path evidence criterion are recorded in [`experiments/model-only-shadow-hosted-runs-2026-09-28.md`](experiments/model-only-shadow-hosted-runs-2026-09-28.md).

The offline `scripts/source_record_decision.py` contract translates a source-auditor record to TypeSafe's native `{model,state,questions}` request and parses its `{model,request_id,answers}` response. It consumes the existing `shadow-source-audit.v1` record shape, validates references against caller-supplied evidence IDs, deterministically selects at most one record by a stable hash ordering, and asks one typed `source-record-jev.v1` question with an explicit `UNCERTAIN` category. Its single invocation bounds the source and Jev transports with one deadline; Jev receives only the remaining time, and late results remain incomplete. In the sealed-artifact bridge, the source call has already completed, so the wrapper separately caps the Jev call at 90 seconds; it does not claim a shared end-to-end deadline. Missing or abstained source records leave Jev `not_run`; a missing native answer is incomplete, not an abstention. Endpoint model identity is checked against the configured model (or a versioned ID when configured as `jev-latest`), but remains endpoint-reported rather than authenticated. The result is hash-only for case/record identity and reports selected/unselected counts, transport invocations, and zero retries. Its advisory choice cannot set disposition and has no writer comparison.

`SourceRecordTransport` is a separate adapter for this contract. It accepts only the exact `source-record-jev.v1` native state, enforces the configured model and operator-supplied endpoint, caps request/response bytes and time, blocks redirects, and makes one HTTP attempt. Its URL policy mirrors `ClaimTransport`: HTTPS operator routes ending in `/systemone` are accepted, and explicitly configured loopback routes are available for local System 1; endpoint configuration must come from trusted operator state, never PR/task input. Fake-opener tests exercise the request validation and transport boundary without network access. Candidate `ClaimTransport` semantics are unchanged. This proves transport safety and contract plumbing only, not source provenance, semantic accuracy, recall, calibration, or release readiness.

The script-only `scripts/sealed_source_record_integration.py` bridges a supplied `run_shadow_audit` result with no writer candidate to that separate native Jev path. `scripts/run_sealed_source_record_jev.py` is a separate operator CLI for the frozen PR464 case: it checks the packet against the pinned plan and evaluation identity, verifies the private manifest/request/response/seal chain, requires source `http_attempted`, and permits at most one TypeSafe call with a 90-second and 64 KB cap. By default it writes a new mode-0700 directory containing only a mode-0600 hash-only receipt. An operator may explicitly add `--write-private-advisory-summary` to also write a separate mode-0600 JSON summary in that same private directory. The optional summary contains only schema version, frozen case/snapshot/plan bindings, the selected record ID hash when one is recorded, source count/status, request/response hashes, and Jev status/typed choice or an explicit no-choice status; it contains no source text, probabilities, confidence, model response, or credential. A completed source audit can have records while Jev remains `not_run` before a record hash is emitted; the summary preserves that state and any constructed Jev request hash. This summary is private-only and is not in the workflow artifact upload allowlist. Run the CLI only after the source-only `run_shadow_audit.py` invocation has produced the private artifacts, with a trusted TypeSafe `decision.json` and explicit `--live`; the flag does not change the hosted runner or workflow's zero-call behavior when no writer candidate exists. Receipt accounting distinguishes the prior source HTTP attempt, Jev HTTP attempt, and the bridge's local source replay callback; retries remain zero, and the outcome remains `incomplete` with `disposition: not_set` and no writer comparison. These hashes and bindings do not authenticate origin: a caller able to replace the supplied result and all its artifacts can construct a self-consistent substitute. This plumbing does not establish semantic quality, recall, calibration, or release readiness; the advisory choice is not calibrated and cannot gate a decision.

The receipt sanitizer now accepts the existing v1 hash-only schema for both legacy zero-call/no-candidate receipts and a future bounded source-only receipt: exactly one source-auditor attempt, an optional single source-record Jev attempt only after a completed source audit, and zero claim-auditor attempts. The dispatched-call ceiling is two, per-role attempt counts enforce zero retries, and every no-candidate receipt remains `incomplete` with no extra disposition or PASS field. Fake validator cases cover valid source-only/optional-Jev shapes and reject false PASS claims, claim-auditor activity, retries, over-budget calls, and inconsistent role accounting. This is receipt-contract preparation only; the live runner does not emit this shape.

Use the roles for different questions, not as votes on one answer:

1. The writer LLM reviews the frozen case and trusted profile and emits candidate findings with stable IDs and source references.
2. Jev independently assesses each writer candidate against the same frozen evidence, keyed to that candidate ID. Preserve its typed decision, abstention, or failure exactly. Do not replace candidate-level assessments with an aggregate score.
3. A source-only LLM auditor reviews the frozen case without seeing writer findings, Jev results, prior teacher labels, or arm identity, and seals its result before either is revealed. This is a check for independently surfaced concerns and evidence gaps, not a complete oracle for missed findings.
4. A separate claim-facing audit may inspect a Jev assessment, its candidate, and the cited evidence. Because it sees the claim under review, label it claim-aware, not blind or prediction-blind. Keep it as a separate supplement unless a versioned contract can represent it without merging it with the source-only audit.

Freeze the case-selection procedure, source snapshots, profile, models, prompts, rubrics, request grouping, limits, and comparison rules before dispatch. Use both a natural-prevalence sample and a separately reported risk-enriched challenge set; never pool their counts. Preserve request and response hashes, role/model/runtime identity, prompt/rubric revision, case identity, and every role outcome. No live target writes or target-code execution are part of this evidence run.

Report per-case and aggregate denominators for writer candidates, Jev assessments, source-auditor observations, claim-audit records, deterministic reference checks, abstentions, disagreements, incomplete results, failures, and not-run roles. Include zero-candidate cases and missing roles. Describe model-to-model relations as observed agreement/disagreement only; do not convert them to correctness labels or use a vote/confidence threshold. A model disagreement stays unresolved until the human owner decides how the advisory should be handled. A source-auditor finding with no writer counterpart is an observed unmatched concern, not automatically a missed defect; a writer finding with no counterpart is not automatically false.

## Decision gates

**Read-only shadow entry.** Start only after the exact source/profile/model/prompt/limit bundle and cases are frozen, the run is authorized as read-only, capture storage is private and bounded, and deterministic preflight verifies source identity and configured limits. The incumbent review remains authoritative. Failure of any preflight check means do not dispatch.

**Read-only shadow qualification.** The package passes only when every selected case and role has exactly one explicit terminal state (completed, failed, incomplete, abstained, not run, or unavailable); all candidate IDs and role outputs reconcile; every source reference has an explicit deterministic snapshot/location/changed-range status; every required deterministic control reports a status; and there are zero safety/control invariant violations, zero configured-limit overruns, and zero cases where stale, partial, failed, or unknown required coverage is presented as current or complete. Unknown or missing checks fail this gate. Publish no review and change no disposition. This gate accepts traceability and bounded operation only, not model quality.

**Future advisory publication.** A read-only pass does not authorize publication. Before an owner may authorize a narrowly scoped, non-blocking advisory publication canary, require the qualified shadow package, exact current-head verification immediately before the write, least-privilege writer identity, tested duplicate/ambiguous-submit recovery, and deterministic effect receipts. The deterministic reducer remains authoritative for disposition and the union of accepted blockers; writer, Jev, and auditor outputs may never remove an accepted blocker or override its status. The publication artifact must preserve every accepted blocker ID and its evidence. For each additional claim eligible for publication, require a stable candidate ID, resolved in-snapshot reference and changed-range status, a completed candidate-bound Jev record, and a separately preserved source-only audit. Quarantine a claim when a required record is missing, incomplete, abstained, or structurally contradictory; do not resolve disagreement by voting. Record withheld claims and denominators. Keep publication explicitly advisory and unable to affect merge eligibility. Obtain a separate, explicit owner authorization for the live canary; successful deterministic checks and model agreement do not create that authorization or establish that a claim is true.

**Future cutover or Droid retirement.** Do not infer replacement quality from this model-only track. Before a reversible cutover decision, require repeated normal-workflow shadows on a frozen, owner-selected natural-prevalence sample and a second project/profile; complete model-role and deterministic-check accounting; no unresolved deterministic safety, freshness, coverage, or publication-control violations; documented operating cost/latency and abstention/disagreement distributions; an observed rollback/recovery rehearsal; and a named owner who explicitly accepts that semantic error rates and general accuracy remain unknown. Keep the incumbent available through the rollback window. Any model, prompt, rubric, or profile change invalidates the associated comparison and requires a new frozen run. This is an operational risk-acceptance decision, not a quality or calibrated-accuracy gate. If the owner requires a quantified quality claim, it cannot be made without independent labels.
