# PR Review Harness contracts

Status: proposed documented contract for the architecture and later specification. No executable schema or implementation is defined here. Field names are canonical for the design package; a requirement without verified runtime support remains a proposal.

## Contract conventions

- UTF-8 JSON-compatible records are exchanged across process and adapter boundaries. Timestamps use RFC 3339 UTC. SHA values are full Git object IDs, never abbreviated identifiers.
- IDs are opaque strings with stable meaning within their stated namespace; callers must not parse them. A retried logical operation reuses its idempotency key. A new run receives a new `run_id`.
- Unknown fields may be ignored only when the receiving contract version explicitly allows extension; unknown enum values, unsupported primitives, absent required fields, invalid envelope/payload types, and invalid cross-record references reject the whole request/result atomically. No silent defaults for policy, identity, budgets, provider/model, or disposition. Narrow item-level validation exceptions are defined for untrusted candidate records and context-gap proposals: the result wrapper must still be valid, and each malformed item is retained or rejected with a typed item error without discarding unrelated well-formed items.
- PII and secrets must not be placed in contract records unless the field explicitly identifies reviewed source evidence. Credential values are forbidden from every record, prompt, artifact, and log.

## Core records

### ReviewRequest

Required fields:

| Field | Type | Meaning |
|---|---|---|
| `contract_version` | string | Exact major/minor contract identifier. Unsupported major versions reject preflight. |
| `run_id` | string | Caller-supplied idempotent run identity or generated by CLI; unique per repository and invocation. |
| `repository` | object `{host: string, owner: string, name: string}` | Canonical repository identity. No inferred default repository. |
| `pull_request_number` | integer > 0 | Target PR. |
| `base_sha`, `head_sha` | full SHA string | Immutable expected review revisions. |
| `event_id` | string | Stable source event identity for duplicate suppression. |
| `project_profile_version` | string | Exact trusted profile revision. Missing/invalid version is a preflight rejection. A named profile that cannot be loaded or reconciled follows explicit unsupported/incomplete policy before worker dispatch; it never downgrades required lenses. |
| `mode` | enum `LIGHT | FOCUSED | DEEP | AUTO` | Requested mode. AUTO applies deterministic versioned routing and risk floors. |
| `provider_plan` | array of `ProviderRequirement`, possibly empty | Explicit configured provider/model/runtime and required semantic capabilities; no model discovery or substitution at runtime. Empty is valid only when trusted profile permits a provider-free baseline; provider-dependent scopes remain NOT_STARTED and cannot support APPROVE. |
| `limits` | `RunLimits` | All finite ceilings required, including wall-clock deadline, max concurrent scopes, max provider calls, max retries per task, max input/output tokens or bytes, and estimated monetary cap when provider pricing is configured. |
| `effect_policy` | enum `READ_ONLY | PUBLISH_REVIEW` | Initial supported pilot value is READ_ONLY. PUBLISH_REVIEW requires separately enabled policy and permission preflight. |

Preflight rejects missing or invalid identity, SHAs, profile version, limits, provider binding, unsupported semantic primitive, unknown provider, or unauthorized effect policy before dispatch. Optional providers are identified as optional in their requirement and cannot silently stand in for a required provider capability.

### ReviewSnapshot

Required fields: `snapshot_id: string`, `run_id: string`, repository identity, PR number, `base_sha`, `head_sha`, `event_id`, `created_at: timestamp`, `project_profile_version: string`, `inventory: array<ChangedUnit>`, `trusted_context_refs: array<EvidenceRef>`, `ignored_or_generated: array<ScopedReason>`, and `snapshot_hash: string`.

A `ChangedUnit` has `unit_id: string`, `path: string`, `kind: enum {human_code, documentation, config, test, generated, binary, unknown}`, `change: enum {added, modified, deleted, renamed}`, optional `old_path: string`, optional line ranges, and `diff_hash: string`. Every changed file must be represented exactly once by current path (plus old path for rename); any omitted, duplicate, unparseable, or unreadable file is a coverage gap. Generated status requires trusted rule/provenance or is `unknown`.

Snapshot data is immutable. Context retrieval adds evidence references and coverage events; it does not mutate the snapshot or silently switch head/base. Every file/context payload is keyed to the snapshot and hashed.

### RunLimits

Each field is finite and has a unit and policy source. `deadline_seconds`, `max_concurrent_scopes`, `max_provider_calls`, `max_input_bytes_per_task`, `max_output_bytes_per_task`, and `max_context_bytes` are positive numbers; concurrency, call, and byte limits are positive integers. Optional `max_snapshot_context_bytes`, when present, is also a positive integer. It caps aggregate source/context evidence captured into the snapshot and defaults to `max_context_bytes` when absent for legacy compatibility. `max_context_bytes` remains the cumulative serialized provider-input admission budget; the snapshot cap does not replace or increase it. `max_retries_per_task` is an integer >= 0, where zero means no retry. `max_cost_microunits` is a positive integer when known provider pricing is available. If price is unknown and budget policy requires a monetary cap, preflight rejects. No field means “unlimited.” Reservations are made before dispatch; exceeding any limit prevents new work and records the skipped scopes.

Provider request sizing uses the same canonical serializer as dispatch but does not apply transport caps, so planning may measure an oversized unsplit scope before deterministic splitting. Immediately before credential lookup or HTTP, dispatch enforces both the provider adapter request ceiling and `max_input_bytes_per_task`. Measurement never authorizes dispatch.

### ScopeTask and TaskResult

`ScopeTask` required fields: `task_id: string`, `run_id`, `snapshot_id`, `obligation_id: string`, `required: boolean`, `scope_id: string`, `lens: enum {correctness, tests, design, security, performance, maintainability, project_specific}`, `scope_unit_ids: array<string>`, `task_kind: enum {SPECIALIST_FINDINGS, SYSTEM_ONE_ASSESSMENT, DETERMINISTIC_CHECK}`, `output_contract_id: string`, `question_id: string`, `question_version: string`, `provider_binding_id: string` for provider tasks or `check_binding_id: string` for deterministic tasks, `attempt: integer >= 1`, and `idempotency_key: string`. `required` and `obligation_id` are derived from the frozen trusted review plan, never from worker output. A redundant optional task may support a required obligation, but its failure does not reduce coverage if an accepted required result already satisfies that obligation.

The scope and question are fixed before dispatch. Parallel scheduling may only select ready tasks under the finite concurrency/budget limits. A task cannot request additional scopes, tools, retries, context, budget, or policy. A semantic result contains one `SemanticAssessment` and may include `context_gap_proposals: array<ContextGapProposal>`. `SemanticAssessment` fields are: `assessment_id: string`, `question_id: string`, `outcome: enum {SUPPORTED, NOT_SUPPORTED, UNCERTAIN, CONTRADICTED}`, `evidence_refs: array<evidence_id>`, `observation_support: enum {SUPPORTED, NOT_ESTABLISHED, CONTRADICTED}`, `consequence_support: enum {SUPPORTED, NOT_ESTABLISHED, CONTRADICTED}`, `rule_connection_support: enum {SUPPORTED, NOT_ESTABLISHED, CONTRADICTED}`, `introducedness: enum {INTRODUCED, REEXPOSED, PRE_EXISTING, UNKNOWN}`, `assumptions: array<string>`, `uncertainties: array<string>`, and `summary: bounded string`. Every `SUPPORTED` claim state needs at least one matching evidence reference. `NOT_ESTABLISHED` means the answer did not establish the claim; it is not an independently proven negative. `CONTRADICTED` requires evidence that conflicts with the claim. `outcome` summarizes the answer across claims and cannot override an individual claim state. `introducedness=UNKNOWN` explicitly records unknown provenance. No field may be null or omitted. `ContextGapProposal` fields are: `proposal_id: string`, `evidence_kind: enum {caller, implementation, test, configuration, contract, trust_boundary, provenance, other}`, exactly one of `target_unit_id: string`, `target_path: string`, or `target_symbol: string`, `rationale: bounded string`, `related_candidate_ids: array<string>` (task-local candidate references at model boundary; controller rewrites them to canonical IDs), `related_evidence_ids: array<string>`, and `required_lens: lens enum`. The result envelope and the proposal-array type are validated atomically; each proposal item is then validated independently. An invalid proposal item is preserved in diagnostics as INVALID, excluded from retrieval, and does not invalidate an otherwise valid assessment or finding list. A malformed/missing/unsupported required assessment invalidates the task result.

Proposals are data only: the deterministic controller validates them against allowlisted retrieval boundaries and policy, then decides whether to fetch and dispatch a new task under fresh budget reservation. Models cannot choose a retrieval API, command, tool, or arbitrary path, and a proposal never itself authorizes retrieval.

#### Dynamic context follow-up (`context-followup.v1`)

A dynamic `REQUIRED_CONTEXT` follow-up carries a bounded `context_followup` object with `contract_version`, `snapshot_id`, `proposal_id`, `parent_task_id`, `parent_obligation_ids`, `followup_obligation_id`, `required_lens`, `scope_unit_ids`, `evidence_kind`, a single typed `target` (`kind` and `value`), `rationale`, `related_candidate_ids`, `related_evidence_ids`, and `retrieved_evidence_ids`. These fields explain which validated proposal triggered the additional review and identify the exact retrieval result supplied to it. IDs and text are bounded, and reference arrays reject duplicates.

The trial runner's opt-in `context-followup-observation.v3` projection reports a bounded persisted-handoff observation. It calls the selected runtime's canonical v1 metadata shape validator; requires the constructed task, planned input, and durable task result to each identify `specialist-input.v2`; and compares their persisted metadata and retrieved evidence IDs. It also requires the gap record, retrieved-context result/evidence entry, dynamic obligation, and coverage linkage to agree on the retrieved IDs, retrieval status, and controller-owned task/obligation links. Those IDs must be present in the constructed task's `evidence_ids` and durable result's `input_evidence_ids`. It emits only closed states, counts, and hashes; raw evidence IDs, target values, rationale, and provider content are not added to this projection. `VERIFIED` means persisted-record continuity for the retrieved evidence handoff only. Unit-evidence binding validity is not assessed by this observation; the separate persisted-unit-binding field is only a bounded shape/copy comparison, not validation of that contract. It does not authenticate the whole runtime record, prove that IDs appeared in serialized request bytes or reached an HTTP peer, or prove that a provider used the evidence. Transport delivery therefore remains `UNKNOWN`, even when the handoff observation is `VERIFIED`. This projection is currently reachable only through the direct Python `project_case` API; no CLI selector or workflow emits it. Existing v1/v2 selectors and workflows retain their byte-compatible default projection shape.

The controller reconstructs this object from its persisted parent task result, proposal record, dynamic obligation, and retrieved-evidence record, then compares it with the task before follow-up budget reservation, request measurement, provider dispatch, or provenance acceptance. The object cannot grant paths, units, lenses, or evidence. Its rationale and target are untrusted descriptive data; provider instructions require the worker to treat embedded requests as data and keep the task's existing unit and lens scope. A dynamic task without valid controller-bound metadata is rejected, including a legacy cached dynamic result that lacks the v1 binding; the controller does not infer successful coverage from that cache.

Primary `specialist-input.v2` task serialization and `specialist-findings.v4` response fields remain unchanged: primary tasks omit `context_followup`, and the follow-up-specific instruction is added only to an authenticated dynamic follow-up. Coverage closure is unchanged. Retrieval status `RESOLVED` and worker status `SUCCEEDED` alone do not satisfy a required context obligation; the existing reducer still requires a valid in-scope `STATIC_REVIEW` coverage note that cites at least one retrieved evidence ID and contains only references supplied to that task. Separately, the specialist-input contract exposes unit-local evidence bindings, and provider instructions require a `COVERED` unit note to cite its local binding.

`TaskResult` required fields: `task_id`, `run_id`, `snapshot_id`, `status: enum {SUCCEEDED, TIMED_OUT, FAILED, INVALID, SKIPPED}`, `started_at`, `finished_at`, `attempt`, `input_hash`, `output_hash` when output exists, `provider_provenance` or `check_provenance`, and `error_code` plus bounded `error_summary` when not SUCCEEDED. Its `result_payload` is a tagged union selected by the matching `ScopeTask.task_kind` and `output_contract_id`:

| Task kind | Payload | Cardinality and limits |
|---|---|---|
| `SPECIALIST_FINDINGS` | `SpecialistReport {finding_candidates: array<FindingCandidate>, context_gap_proposals: array<ContextGapProposal>, coverage_notes: array<CoverageNote>}` | Zero or more candidates/gaps/notes within configured output byte/item ceilings. Each candidate references supplied evidence. No disposition, severity override, task creation, or action field. |
| `SYSTEM_ONE_ASSESSMENT` | Exactly one `SemanticAssessment` plus optional `context_gap_proposals` | One answer to one fixed question and declared semantic primitive; output contract rejects extra assessment records or workflow/action fields. |
| `DETERMINISTIC_CHECK` | `CheckReport {check_id, outcome: enum {PASS, FINDINGS, UNKNOWN, ERROR}, finding_candidates: array<FindingCandidate>, evidence_refs: array<EvidenceRef id>, diagnostics: array<bounded string>}` | One check result for the declared binding; PASS is valid only with provenance and captured result evidence. UNKNOWN/ERROR do not count as completed coverage unless the profile explicitly declares the check optional. |

`CoverageNote` has `unit_id` or explicit whole-scope ID, `state: enum {COVERED, PARTIAL, NOT_COVERED}`, `reason_code`, and `evidence_refs`. It records scope only; it cannot declare an obligation satisfied unless the controller verifies its task/result contract.

Specialist reports and deterministic checks may propose candidate findings without establishing that their substantive claims are true. Reconciliation applies evidence and semantic-adjudication rules below. No task result can contain next actions or tool calls.

Conflicting successful results for one `task_id` with differing `output_hash` are not last-write-wins: quarantine both, mark the scope ambiguous, and require reconciliation or leave it PARTIAL.

### ProviderRequirement and provenance

`ProviderRequirement` fields: `provider_id: string`, `endpoint_id: string`, `model_id: string`, `runtime_version: string`, `required: boolean`, `native_contract: string`, `supported_primitives: array<string>`, and `credential_reference_name: string` (name only, optional for local/no-credential runtime). Never include credential material. The adapter must positively declare the requested primitive supported before dispatch. Unknown providers, endpoints, models, native contracts, or primitives fail preflight atomically. No fallback or cross-provider equivalence is implied.

Provenance records provider/model/runtime identifiers as reported by the endpoint, request contract and version, question version, timestamp, input/output hashes, token/cost usage if reported, and whether usage is unknown. Each provider binding declares a capability map from `task_kind`/primitive to its native contract and adapter version. GLiNER and Laya use native contracts; an adapter may expose only capabilities whose meaning and output contract are explicitly defined for that native implementation. A provider that supports finding extraction is not thereby assumed to support `SYSTEM_ONE_ASSESSMENT`. An optional capability may be omitted by planning only when no ReviewRequest or required task asks for it; any explicitly requested unsupported primitive or task kind rejects preflight atomically, even if marked optional. Similar shape does not establish semantic or probability equivalence. Jev comparison is optional and advisory unless separately evaluated and authorized.

### EvidenceRef, FindingCandidate, and AcceptedFinding

`EvidenceRef` required fields: `evidence_id: string`, `snapshot_id`, `source_kind: enum {diff, repository_file, test_result, tool_result, profile, model_assessment, human_note}`, `path` or `external_source_id`, optional line/byte range, `content_hash: string`, `captured_at: timestamp`, and `trust: enum {trusted_policy, repository_evidence, untrusted_pr_content, generated_result}`. Evidence text is bounded and stored separately by content hash when appropriate. Trust labels describe source authority, not truth.

A `FindingCandidate` has required `candidate_id`, `task_id`, `snapshot_id`, `unit_id`, `location` (path plus valid changed line/range or explicit file-level location), `title`, `observation`, `consequence`, `rule_or_contract`, `evidence_refs: nonempty array<EvidenceRef id>`, `reasoning_kind: enum {observed, inferred}`, optional `assumptions`, `severity: enum {critical, high, medium, low, informational, unknown}`, and `correlation_hints: array<string>`. Candidate validation is assigned by the harness, not the producer, as `validation_state: enum {VALID, NEEDS_CONTEXT, INVALID}` with `validation_reason: string` and any `missing_evidence_kinds`. If a location cannot be verified against the snapshot, validation is NEEDS_CONTEXT when further bounded context could resolve it, otherwise INVALID; neither can be accepted as a located blocker. Invalid raw candidates remain in the task result by producer reference and validation error for audit.

Producer-local candidate references are scoped to `task_id`; the reconciler assigns canonical `candidate_id` values on receipt and stable `finding_id` values when a candidate enters the cross-task finding ledger. Workers may refer to their own candidate references in same-task context-gap proposals only. The controller rewrites those references to canonical IDs before any follow-up task is issued.

Reconciliation assigns a stable `finding_id` only once the canonical candidate is created. IDs are derived from persisted identity allocation, not model text. Candidate records are immutable; reconciliation status is appended separately.

`AcceptedFinding` includes `finding_id`, `snapshot_id`, `unit_id`, verified location, normalized observation and consequence, evidence references, `status: enum {ACCEPTED, NEEDS_EVIDENCE, UNSUPPORTED, CONTRADICTED, DUPLICATE}`, `severity`, `blocking_class: enum {BLOCKING, NON_BLOCKING, UNRESOLVED}`, `introducedness: enum {INTRODUCED, REEXPOSED, PRE_EXISTING, UNKNOWN}`, `blocking_rationale: string`, `correlation_group_id` (nullable), and reconciliation provenance. Severity describes plausible impact; `blocking_class` separately describes whether the PR disposition must request changes. High/critical severity alone does not make a finding blocking, and low severity alone does not prove it is non-blocking. A finding is eligible for BLOCKING only when evidence identifies a concrete material consequence tied to changed/re-exposed behavior or an explicit trusted project policy, with scope/location validated and no unresolved contradiction. A high-impact pre-existing issue unrelated to this change is not automatically a PR blocker; report it as non-blocking guidance unless a trusted baseline-review rule makes it in-scope. When introducedness, consequence, or policy relevance is unknown, use UNRESOLVED, preserve evidence and uncertainty, and do not count it as an accepted blocker.

Structural validation can establish identity, location, hashes, provenance, and whether evidence was supplied; it cannot establish substantive truth or materiality. Substantive assessment is a bounded, versioned semantic judgment over cited evidence and the applicable trusted contract. Its record must state whether evidence supports the observation, consequence, policy/rule connection, and introducedness; list assumptions and missing context; and return one of `SUPPORTED`, `NOT_SUPPORTED`, `UNCERTAIN`, or `CONTRADICTED`. Deterministic reconciliation checks that the assessment answers the requested question and cites only available evidence, then applies the explicit blocking policy above. It must not treat model confidence/probability as truth or use a confidence cutoff as a substitute for evidence. `SUPPORTED` is still an advisory model assessment absent independent validation; it does not certify correctness. For policy-sensitive or consequential disputes, route to human review when configured; otherwise retain UNRESOLVED and make disposition INCOMPLETE unless a separately substantiated blocker already requires REQUEST_CHANGES. Unsupported, contradicted, duplicate, or needs-evidence records remain in the ledger and are not silently dropped.

Correlation grouping preserves all member `finding_id`s and evidence; it may identify one root cause with multiple manifestations. Deduplication must not erase distinct impacts, locations, blockers, or provenance. Specialist conflict creates explicit contradiction records referencing all finding IDs; severity is not averaged and no unsupported tie-break is invented.

### CoverageEvent and ReviewResult

The required coverage denominator is frozen before dispatch from the immutable snapshot plus the named trusted project profile. It includes each changed-unit/lens obligation, every required project check, and every required context/security/policy obligation. Each ledger entry has `coverage_id`, `run_id`, `snapshot_id`, `obligation_kind: enum {CHANGED_UNIT_LENS, PROJECT_CHECK, REQUIRED_CONTEXT, POLICY_LENS}`, `obligation_id: string` stable within the profile/snapshot, `required: boolean`, `scope_unit_ids: array<string>`, optional `lens`, optional `check_binding_id`, `state: enum {COMPLETE, PARTIAL, NOT_STARTED}`, `reason_code`, `task_ids`, `evidence_refs`, and timestamps. Required obligations define the aggregate denominator; optional task/obligation failure does not make required coverage PARTIAL, though it remains visible in the ledger. A required project check is independently represented even when it spans multiple changed units; it cannot be hidden inside a general lens entry. Added obligations discovered through authorized context expansion are recorded with parent obligation IDs, without removing or rewriting the initial denominator.

`COMPLETE` requires the planned obligation finished with valid results; “no finding” is recorded as a completed result, never as missing coverage. Invalid, timed-out, skipped, ambiguous, or out-of-budget required obligation is PARTIAL or NOT_STARTED. Overall `coverage_state` is COMPLETE only when every required obligation is COMPLETE, NOT_STARTED when no required obligation began, and PARTIAL in all other cases (including a mixture of completed and not-started obligations); preflight REJECTED remains a separate run status.

The opt-in `required-context-coverage-diagnostic.v1` projection joins each projected REQUIRED_CONTEXT coverage row to its bounded closure-note observation and, when present, the matching context-follow-up observation by exact obligation/task IDs. It exposes only allowlisted coverage states/reason codes, note-result/failure-count enums, and bounded opaque IDs; missing, malformed, duplicate, truncated, or conflicting linkage is UNKNOWN, PARTIAL, or MISMATCH. It is available through direct Python calls to `project_case(..., include_required_context_coverage_diagnostic=True)`; existing selectors and CLI artifacts do not include it. The internal helper requires both the case projection and its in-memory durable records, and rejects projected-only inputs as evidence of source completeness. A historical sanitized manifest cannot establish raw-source completeness; the diagnostic must be generated from the durable records during projection. The projection reports persisted note/ledger evidence and does not recompute coverage, infer why a reviewer chose a note state, prove delivery, or change reducer decisions. Note text, prompts, provider responses, source content, secrets, and target code are not projected.

`ReviewResult` required fields:

| Field | Type | Semantics |
|---|---|---|
| `run_id`, `snapshot_id` | string | Identity of one run and immutable input snapshot. |
| `base_sha`, `head_sha` | full SHA string | Revisions actually reviewed. |
| `project_profile_version` | string | Trusted policy/context revision used. |
| `coverage_state` | enum `COMPLETE | PARTIAL | NOT_STARTED` | Required review coverage status. |
| `freshness` | enum `CURRENT | STALE | UNKNOWN` | Whether the observed PR head still matches at final check. UNKNOWN cannot support approval or publication. |
| `disposition` | enum `APPROVE | REQUEST_CHANGES | COMMENT | INCOMPLETE` | Review recommendation from deterministic reducer. |
| `merge_eligibility` | enum `UNKNOWN | ELIGIBLE | INELIGIBLE | NOT_EVALUATED` | Repository merge-rule assessment only; defaults to NOT_EVALUATED if not explicitly checked. |
| `findings` | array of `AcceptedFinding`/unresolved findings | Stable IDs and statuses, including every accepted blocker. |
| `coverage_ledger` | array of coverage entries | Denominator and each complete/missing/failed scope. |
| `report_sections` | object with exactly four required arrays | `blockers`, `suggested_improvements`, `specific_strengths`, `future_guidance`. |
| `created_at`, `completed_at` | timestamps, completion nullable | Start and terminal report times. |
| `result_hash` | string | Hash of canonical result excluding this hash. |

Disposition reducer invariants: APPROVE requires freshness CURRENT, coverage COMPLETE, no finding with `blocking_class=BLOCKING`, no unresolved required lens/context gap or policy-sensitive finding, and profile/policy validity. REQUEST_CHANGES requires at least one accepted finding with `blocking_class=BLOCKING`; it may coexist with PARTIAL coverage, which must be prominently disclosed. INCOMPLETE applies when no blocker forces REQUEST_CHANGES and required coverage/policy is incomplete, a consequential assessment is unresolved, or freshness is not current. COMMENT applies to completed current coverage without blockers when improvements or guidance merit a nonblocking review; a completed empty review may use APPROVE only if all approval preconditions hold and the configured policy permits it. No model output directly sets disposition.

Merge eligibility is computed independently from the repository’s configured required checks and branch protections; review result alone never establishes it. If required GitHub state cannot be read or rules are unconfigured, use UNKNOWN or NOT_EVALUATED, never ELIGIBLE by default.

## Editorial contract

The renderer emits exactly four top-level sections in this order: **Blockers**, **Suggested improvements**, **Specific strengths**, **Future guidance**. Each listed finding references its stable ID. Every accepted blocker ID appears in Blockers and is linked to its verified evidence and location. Non-blocking suggestions reference accepted or clearly labeled unresolved evidence. Strengths require positive evidence references; if none exist, the array is empty. Future guidance is optional and evidence-linked or labeled as a proposal. Editorial synthesis may summarize but cannot create/delete IDs, alter finding status/severity, omit a blocker, change coverage/freshness/disposition, or claim checks not in the ledger.

## Publication contract (future, disabled in pilot)

An effect request is valid only when `effect_policy=PUBLISH_REVIEW`, operator/trusted configuration enables publishing, required least-privilege authorization is present, `freshness=CURRENT`, result hash and head SHA are rechecked, and repository write scope is limited to the requested review action. The idempotency key is a hash of `{repository, pull_request_number, head_sha, disposition, result_hash, effect_type}`. The publisher queries existing effect state before retrying an ambiguous response. It records requested, confirmed, rejected, or unknown outcome separately from `ReviewResult`. No merge, source edit, or silent retry with a changed result is supported.

## CLI and Actions boundary

The CLI accepts explicit repository, PR, expected SHAs, profile version, mode, provider plan, finite limits, and effect policy; configuration files may supply values only when their resolved version/hash is recorded. Exit codes are: `0` when a valid terminal `ReviewResult` and durable report are written, including disposition INCOMPLETE; `2` for atomic preflight request/config rejection before dispatch; `1` for internal/runtime failure without a valid durable terminal report. It does not interpret prose output as workflow commands.

### CLI diagnostic contract revision 2

Revision 2 updates the interpretation of the existing JSON error envelope; it adds no field and changes no exit code. In `--json` mode, a preflight failure remains `{"error": <stable-code>, "exit_code": 2}`. Engine request validation and saved-state/resume validation may now expose these additional finite codes: `invalid_review_request`, `run_id_already_exists`, and `resume_state_invalid`. The older generic `preflight_rejected` remains valid for CLI preflight paths that do not have a more specific typed reason. Runtime failures continue to use exit 1 and their existing runtime diagnostic contract. A consumer that does not recognize a code must classify it as `other` or otherwise preserve failure; it must not treat an unknown code as success or infer that dispatch occurred.

The recovery rehearsal accepts only the exact legacy `preflight_rejected` or current `resume_state_invalid` code for its profile-drift case, requires exit 2, and independently checks zero added fake-provider requests and unchanged checkpoint bytes. The syscall observer and its prepare-smoke summary retain only the closed diagnostic allowlist and map unknown strings to `other`; these labels do not change observer completeness, exit classification, or acceptance criteria. Operational troubleshooting is documented in [Operations](../OPERATIONS.md), and the profile-drift fixture is specified in [Recovery Rehearsal](../RECOVERY-REHEARSAL.md).

The Actions adapter maps event and read-only GitHub data to `ReviewRequest`, passes a narrowly scoped credential reference by environment/secret name, and publishes the report as a workflow artifact in the initial pilot. It must not grant write permissions or expose secrets to untrusted code execution. Head-controlled tests run in a separate secretless job and return bounded result artifacts. Exact event, permission, cache, and action-pin settings are repository-specific and not established by this contract.

## Implementation clarification (0.1.1 pilot)

The initial historical-commit adapter uses `documentation` as an explicit ChangedUnit kind and records HISTORICAL_SNAPSHOT freshness basis; CURRENT in this mode verifies only the requested immutable local snapshot, not a live PR. No PR publication is available. Event mode separately binds repository/PR/event identity and checks current GitHub head. Scalar provider-field simplifications and unsupported features are recorded in ../VERIFICATION.md before delivery.
