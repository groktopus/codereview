# Stateless GitHub Actions publication design

Status: bounded design for implementation review. No review has been posted, and this document does not authorize a live write.

## Decision

Replace the normal publication path's required local SQLite effect store with a protected GitHub Actions publisher that uses GitHub as its only durable coordination surface: Actions workflow runs and artifacts record attempts; submitted PR reviews carry the externally visible effect marker. The analysis workflow stays hosted and read-only. The publisher runs only from a protected default-branch workflow after it has independently admitted the exact analysis run and result artifact. It never checks out, imports, or executes pull-request code.

The design does **not** promise exactly-once delivery. GitHub's review-create endpoint documents no idempotency-key contract. Actions concurrency reduces overlapping publisher jobs, but it is not an atomic effect store. If the review POST may have reached GitHub and the response is missing or ambiguous, the state is `UNKNOWN`; an absent marker is not proof that GitHub did not accept the review. Automated reruns must not POST again while that state is unresolved.

A single immutable effect is permitted for each `(repository_id, pull_request_number, head_sha, effect_type)` slot. The canonical body and sealed result hash are bound into an effect key and marker. A second result for the same slot is a conflict, even if its body differs. Changing the PR head creates a new slot. This policy avoids silently replacing one review with another on the same revision.

## Why the receipt precedes the review

Each authorized publication attempt first writes a small, versioned `SUBMISSION_STARTED` receipt to a uniquely named artifact on the **publisher workflow run**. The receipt includes the slot identity, effect key, result hash, canonical review-body hash, upstream analysis run ID/attempt, publisher run ID/attempt, trusted workflow identity, and protocol version. It contains no provider prompt, credential, or full review body. The workflow must observe successful artifact upload before it invokes the single review POST. If upload fails or its outcome is ambiguous, it does not call the review endpoint.

A later run scans a bounded, complete set of publisher workflow runs and reads run-scoped receipts. It cannot filter publisher runs by the reviewed PR head: for a `workflow_run` event, GitHub sets the publisher run's `GITHUB_SHA` to the last commit on the default branch, not the PR head. Each prior run must therefore be correlated through its receipt to the exact upstream analysis run, then through that analysis run's API record to the repository/PR/base/head. A missing receipt cannot prove that a run was unrelated or that no POST occurred; it produces `UNKNOWN`. One exact submitted review marker from the configured actor confirms the effect. A prior receipt without one exact matching review is `UNKNOWN`, so no new POST is allowed. Missing or expired receipt history, incomplete pagination, duplicate receipts, or a read/API error also produce `UNKNOWN`; callers cannot interpret unavailable history as “not published.” A receipt may conservatively block publication if the workflow stopped after recording intent but before making the POST. That false block is preferable to an automatic duplicate review.

I considered using a GitHub pending review as the receipt. The API allows creating a pending review and later submitting it by review ID, but it documents no atomic uniqueness guarantee for pending reviews by actor/PR. It also adds a second review mutation and leaves draft reviews to reconcile after cancellation. It therefore does not replace the receipt or make submission idempotent; this design keeps one direct review POST after the Actions receipt is durable.

For a brand-new slot, a complete review-marker lookup plus a complete receipt-history scan with no prior attempt permits one attempt. The marker embeds the effect key. Reconciliation requires the expected repository and PR, configured bot login, exact head SHA, marker, canonical body hash and expected review state. More than one match, a body mismatch, another marker for the same actor/head with a different effect key, or any truncated scan is `UNKNOWN` or `CONFLICT`; none permits a second POST.

The receipt artifact is GitHub-hosted persistence, not a database or a signature. Its authority comes from retrieving it through the exact protected publisher workflow run and verifying the GitHub-reported artifact digest, run ID/attempt, workflow ID/path/ref/SHA, repository ID and protocol version. A hash alone proves byte consistency, not who created the bytes. Artifact expiration or manual deletion removes recovery evidence; if a prior run could have attempted publication, the publisher must stop as `UNKNOWN` and request operator reconciliation.

## GitHub concurrency and ordering

Use a job-level concurrency group keyed by numeric repository ID and admitted PR number, for example `pr-review-publish-${{ github.repository_id }}-${{ needs.admit.outputs.pull_request_number }}`. Configure `queue: max` with `cancel-in-progress: false`. The admission job has read-only permissions; only the gated publisher job receives `pull-requests: write` and `actions: read`. A publisher run canceled before the receipt is durably uploaded cannot proceed to POST. A canceled run after the receipt exists is recovered by marker lookup and otherwise remains `UNKNOWN`.

GitHub documents a maximum of 100 pending jobs for `queue: max`, and says dispatch order is not guaranteed even though queued jobs wait FIFO from when they began waiting. Queue overflow and incomplete admission scans fail closed. Every queued run re-reads the current PR and checks repository identity, open/non-draft state, base SHA and head SHA before preparing a receipt and again immediately before POST. A stale result is skipped; it is never relabeled to the new head. A head change can race the final read and the POST, so the review always carries the exact admitted `commit_id`; post-submit reconciliation reports if the PR moved meanwhile, without attempting another review.

Canonical result selection must not depend on which publisher job gets dequeued first. Before publication, the admission code enumerates all completed runs of the pinned analysis workflow that match the same repository ID, PR, base/head, profile hash and harness commit. It selects the minimum numeric `(run_id, run_attempt)` among eligible successful runs, using a complete bounded listing. If a lower-ID candidate is still running, the current publisher defers without a receipt; that candidate's completion event triggers a fresh selection. A selected candidate with a missing, expired, invalid or mismatched artifact blocks the slot; the publisher does not silently fall through to a different result. Runs that exceed the configured scan/page cap, or any incomplete listing, yield `UNKNOWN`. The target caller must restrict analysis triggers to reviewed PR events and disable manual result substitution; rerunning a later attempt does not replace an already selected immutable slot.

Concurrency serializes only jobs using this repository concurrency group. It does not serialize local tools, other workflows, other GitHub Apps, or human reviewers, and it cannot atomically compare the PR head with the review POST. Enforce one authorized writer workflow and actor through repository policy, inspect existing reviews from the configured actor for the same head, and treat any conflicting writer state as `CONFLICT`. Do not describe concurrency as exactly-once or global mutual exclusion.

## Trust, identity and data boundaries

The read-only analysis workflow fetches immutable base/head Git objects and emits a fixed result bundle. A separate workflow triggered by completion of the named analysis workflow runs from protected default-branch code. `workflow_run` is a privilege boundary: it can access secrets and a write-capable token even when the source PR is from a fork. The publisher therefore fetches the run and artifact metadata from GitHub, verifies the exact upstream repository ID, workflow ID/path/ref/SHA, event, base branch, run ID/attempt and successful conclusion, then strictly parses only fixed JSON entries from that run's artifact. It never trusts artifact-supplied identity on its own and never checks out the PR.

Admission cross-checks the artifact's repository ID/name, PR number, base/head SHAs, profile version/hash, harness repository and full commit SHA, provider/model alias, result hash and contract versions against independently fetched Actions and PR API data and trusted default-branch policy. It verifies the GitHub artifact digest, result integrity hash, deterministic disposition, required coverage, accepted findings/evidence/locations and canonical rendered report. The validator follows the existing disposition contract: `APPROVE` requires complete eligible required coverage and valid policy; a supported `REQUEST_CHANGES` may retain a validated blocking finding while other required coverage is partial; an allowed terminal incomplete review may publish as `COMMENT`. Invalid findings, stale source binding, noncanonical reports and inconsistent dispositions are rejected. Re-read PR state immediately before the effect. A cryptographic artifact attestation can be added only after a canary verifies the actual signer and reusable-workflow claims; the Actions run association and artifact digest are required independently of attestation.

The write job receives only the permissions needed for the selected target and uses the authenticated GitHub Actions bot identity (or one explicitly allowlisted GitHub App actor). It submits one review with one `event` and one body; it cannot merge, edit source, change labels, dispatch another workflow, or run model-proposed actions. No provider credential is needed in the publication job. The result and receipt artifacts can contain review text and evidence references: apply repository artifact access/retention policy and keep raw prompts and credentials out of both.

## Failure and recovery contract

| Condition | Outcome | Automatic retry? |
|---|---|---|
| Artifact/result/run identity, policy, actor, disposition, or current head fails before receipt | `REJECTED` or `STALE`; no review POST | A new successful analysis for a new/valid head may run |
| Receipt artifact upload returns failure or times out | `UNKNOWN` if persistence is uncertain; no review POST in this run | Reconcile the publisher run/artifacts first; never infer absence from failed upload response |
| Review POST returns a matching review and actor/head | `CONFIRMED`; record outcome receipt if possible | Duplicate delivery performs read-only reconciliation |
| Review POST times out, connection resets, runner is canceled, or response cannot be validated | Query markers once within limits; exact unique match is `CONFIRMED`, otherwise `UNKNOWN` | No automatic POST while the receipt exists |
| Marker/history query is incomplete, rate-limited, malformed, or unavailable | `UNKNOWN` | Read-only reconciliation only |
| Prior receipt exists but marker is absent, body differs, or more than one marker/receipt matches | `UNKNOWN` or `CONFLICT` | No automatic POST; operator reviews Actions run, artifact history and PR reviews |
| Receipt or run evidence expired/deleted | `UNKNOWN` if that run could have attempted publication | No automatic POST; preserve the immutable-head slot pending explicit operator resolution |
| API gives a definitive rejection after the POST was attempted | Record the response and `REJECTED` when its semantics are unambiguous; retain the receipt | No automatic POST for that slot; operator chooses a new head or resolves it |

Never retry the POST merely because a review marker is temporarily absent after a timeout. Recommended initial bounds are 10 review pages at 100 records per page, 100 publisher runs across at most 10 pages, a 16 KiB receipt JSON file, a 1 MiB compressed and expanded receipt bundle, and a 90-second total reconciliation deadline. Owners may lower these values. Hitting any cap before proving a complete scan is `UNKNOWN`. Attempt-history enumeration is likewise bounded and typed. The implementation must not convert permission errors, artifact expiration, pagination changes, or malformed records into an empty successful scan.

A completed success response is checked against the expected `review_id`, actor, commit ID, review state, effect marker and canonical body. If that response is lost, a single bounded GET reconciliation may confirm the review. If no match appears, persist/retain `UNKNOWN`; a later read-only operator reconciliation may discover a delayed review. There is no automatic “unlock,” deletion, edit, dismissal, or replacement path.

## Bounded implementation slice

The current unintegrated adapter slice is implemented in `src/pr_review_harness/actions_publication.py`; fake-transport tests cover exact bundle admission, receipt upload acknowledgement, publisher-run/default-branch SHA handling, bounded run history, fail-closed missing receipts, bot identity, redirects and a one-shot review POST. The history reader enumerates publisher workflow runs across the configured run/page cap and requires prior runs to carry a receipt; thus an unrelated run without a receipt can block another PR. A run count beyond the cap, a rerun attempt whose artifacts cannot be distinguished, an expired/deleted receipt, or history beyond GitHub's retained API view remains `UNKNOWN`. `COMPLETE` describes the full API-visible response within the cap and cannot prove an administrator never deleted a workflow run. No protected workflow, credential canary, upload adapter, or live GitHub write is integrated or verified; keep this capability unavailable until those pieces are bound and canaried.

Implement after design approval, keeping review publication disabled until a protected-workflow canary and owner authorization:

1. `src/pr_review_harness/publisher.py`: retain strict result validation and canonical preview; replace required `SQLiteEffectStore.claim` semantics on the Actions path with an injected attempt-receipt/history interface. Return typed `CONFIRMED`, `CONFLICT`, `UNKNOWN`, `REJECTED`, and `STALE`; only an explicit receipt-upload acknowledgement may advance to one POST. Keep any local SQLite support clearly named legacy/optional until an explicit removal migration, not a hidden fallback.
2. `src/pr_review_harness/github.py`: expose typed bounded reads for the target PR, exact actor, reviews and workflow-run/artifact history; classify pagination completeness and read failures. Validate full 40- or 64-character commit IDs. Add one POST operation with automatic POST retries disabled and a response validator; never retry inside transport.
3. `src/pr_review_harness/cli.py`: remove `--effect-store` as a required argument for the protected Actions route. Add a distinct `publish-actions` entrypoint that verifies exact GitHub workflow/run context via API and requires a successfully uploaded receipt artifact before it can submit. Keep the existing generic `publish` refusal under `GITHUB_ACTIONS=true`; a flag or environment variable alone cannot authorize Actions publication. A local live path without the trusted receipt capability remains unavailable; dry-run preview stays read-only.
4. `.github/workflows/pr-publish.yml` and the target-repository caller: protected `workflow_run` intake, complete deterministic candidate selection, per-PR `queue: max` concurrency, exact run/artifact cross-checking, read-only admission permissions, narrowly gated write job, pre-POST receipt artifact, and no PR checkout or execution. Pin every third-party action by full SHA and do not pass provider secrets to this job.
5. `tests/test_cli.py`, `tests/test_github.py`, `tests/test_publisher.py`, plus a workflow contract test: use a fake GitHub transport and temporary artifact/run listings. Cover queue-order permutations; exact repo/PR/head and bot actor binding; SHA formatting; duplicate same-result marker; same-head different-result conflict; stale-head changes before POST; stale head after POST; receipt upload success/failure/ambiguous response; POST success, timeout-after-acceptance, timeout-before-acceptance and malformed response; marker absence after ambiguity; duplicate/missing/expired receipts; truncated or shifting pagination; max-run/page caps; concurrent duplicate workflow events; tampered result/artifact; no retry after `UNKNOWN`; and no network/write on dry-run. Tests prove harness behavior against the fake transport, not GitHub's undocumented atomicity or a deployed production workflow.

## Deployment prerequisites and owner decisions

The repository owner must choose the target repository ID, protected caller/publisher workflow paths and full-SHA pins, profile hash, allowed dispositions, exact actor/app, artifact access and retention, maximum run/page/byte counts, timeout/deadline and `UNKNOWN` incident owner. The selected provider credential must be explicitly configured in Actions secrets or an organization/environment binding; do not infer a provider from a similarly named secret. The currently observed repository secrets were `DEEPSEEK_API_KEY`, `FACTORY_API_KEY`, and `GPUSLUT_API_KEY`; they do not establish a Nous credential or backend mapping.

Before enabling the publisher, demonstrate with fake transport and then read-only Actions canaries that (a) the called workflow's signer/run identity is represented as expected, (b) run/attempt/artifact enumeration is complete under the caps, (c) queue overflow and cancellation preserve the `UNKNOWN` rule, (d) the exact authenticated bot actor and review response shape match, and (e) no broad write permission reaches the analysis job. A fake transport test is not a live API validation; a read-only canary is not authorization to POST. Keep publication disabled until the workflow, policy, recovery behavior and operator ownership are explicitly approved.
